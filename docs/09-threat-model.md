# 09 · 威胁模型（M9，对齐指导书 §12）

> 范围：BTUnlock 全链路——Android 广播端、Windows 桌面端、C++ 凭据提供程序、本机命名管道。
> 场景定位：**单人自用的个人设备**。指导书 §4.2 明示的两个物理风险（BLE 中继、手机被偷）在协议层面不可根除，处置方式是「明确告知 + 一键撤销」；提供密码学距离证明需要额外可信硬件，明确不做。
> 更新：2026-11-21（M5/M6/M8 落地后）。

## 1. 资产与存放

| 资产 | 存放 | 保护措施 |
|---|---|---|
| Windows 账户密码（明文） | 仅内存与管道传输瞬间 | 落盘为 DPAPI 用户级密文（v=2）；管道 DACL 限 SYSTEM + 录入用户、单实例；不写日志。**残余**：内存中的 string 无清零/防转储，进程被同用户代码转储即可读出 |
| 滚动令牌 HMAC 密钥 | PC：settings.json；手机：App 本地存储 | PC 端为 DPAPI 用户级密文（M6，旧明文自动迁移）；广播中只出现 4 字节 MAC 截断，密钥本身不进入广播 |
| 锁意图 journal | `%APPDATA%\BTUnlock\lock-intent.json` | 只含随机 epoch 与时间戳，无秘密；10 分钟过期 |
| 解锁凭据（user/domain + 密文） | `%ProgramData%\BTUnlock\credential.json` | ACL：SYSTEM + Administrators + 录入用户；v2 仅录入用户可解 |
| 广播负载（设备 ID + 时间戳 + MAC） | 空口明文 | 无机密性——设备 ID 被克隆且无密钥时只能驱动锁屏（安全侧），不能驱动解锁 |

## 2. 信任边界

```text
Android(广播方) ──BLE 明文广播──▶ 桌面 BleScanner          ← 边界 A：空口，无配对/无加密
桌面进程(WPF)   ──NamedPipe(DACL)──▶ CP(LogonUI/SYSTEM)     ← 边界 B：本机 IPC
CP              ──COM(ICredentialProvider*)──▶ LogonUI/LSA ← 边界 C：官方接口，认证决定权在 Windows
桌面进程        ──文件──▶ settings/credential/intent       ← 边界 D：本机文件，ACL/DPAPI
```

## 3. STRIDE 摘要

| 威胁 | 现状与缓解 | 残余 |
|---|---|---|
| Spoofing（伪造广播） | CompanyId+魔数过滤；v2 令牌 HMAC-SHA256 截 4B + 时间窗 ±20s（M6 收紧）。克隆设备 ID 无密钥只能推动锁屏 | 4B 截断非加密强；v1 帧（未配密钥）可被克隆驱动锁屏 |
| Tampering（篡改帧） | MAC 校验失败整帧丢弃 | — |
| Repudiation（抵赖） | 日志记录锁/解锁来源：锁意图归因 AUTO/MANUAL（M5），CP 失败上报计数（M6.6） | 锁屏归因依赖 SessionLock 事件及时到达（120s 窗口） |
| Information disclosure | 密钥/密码落盘均已 DPAPI（M6/M8）；管道 DACL；cp.log 只记用户名不记密码 | 同用户代码执行可解一切（见 §4）；内存明文无清零 |
| Denial of service | 桌面被杀 → CP 查询超时按不在场（fail-closed）；管道占用 → 单实例重建；伪造 F;N 熔断 → 只能造成「更安全」的暂停 | 恶意暂停自动解锁（DoS 级，安全侧） |
| Elevation of privilege | 管道 DACL 拒绝其他用户；CP 不参与登录/UAC；注册表总开关缺省关 | 低权限其他用户不可达管道 ✓；同用户进程等同全权（见 §4） |

## 4. 不可根除的风险（明确告知）

### 4.1 同用户本地代码执行 = 全部失守

任何以**录入用户**身份运行的进程都能：解密 settings.json 与 credential.json 的 DPAPI 密文、连接命名管道拿到 `P;user;domain;密码` 响应、或写注册表关闭组件。DPAPI 与 ACL 只防**跨上下文**（其他用户、重启后裸盘拷贝），不防已攻陷的用户会话——指导书 §6.3 原文承认这一点。缓解边界止步于此：不承诺抵御同用户恶意软件。

### 4.2 BLE 中继攻击（协议不可防）

滚动令牌是共享密钥 + 时间窗，中继者把远处手机的帧原样转发给 PC，PC 无法与"手机真的在附近"区分；RSSI 由中继端信号强度决定，双阈值只是让中继需要稳定的信号注入。**M7 挑战应答同样不解决中继**（指导书 §4.2 原文明示）。真正的距离保证需要 UWB/红外测距或用户交互确认——不在本项目范围内。

### 4.3 手机被偷 / 被远程控制

当前方案的"身份"是手机本地保存的 HMAC 密钥：持有可应答手机（或提取其密钥）的人靠近即可解锁电脑。缓解 = 快速撤销能力，而不是事前防御：

- PC 端：主界面解绑设备 / 清除令牌密钥；「录入 / 管理密码…」改密后旧凭据失效（配合 M6.6 熔断）。
- 组件级：管理员 `reg add HKLM\SOFTWARE\BTUnlock /v UnlockProviderEnabled /t REG_DWORD /d 0 /f` 立即停用。
- 手机端：手机锁屏 + 远程抹除；抹除后密钥消失，广播停止。

### 4.4 隔墙强 RSSI ≠ 距离保证

RSSI 受墙体、天线朝向、多径影响，双阈值 + 驻留只是降噪，不是测距。隔壁强信号可能被判在场（配合 M5 不会解锁非本程序锁定的会话，但会阻止自动锁屏）。

## 5. 用户告知口径（README/UI 统一话术）

- 「手机在附近」≠「手机在你手里」。启用自动解锁意味着：**任何能持续应答已绑定广播的人，都能解锁这台电脑**。
- 自动解锁提交的是保存的真实账户密码（Windows Hello 的等效替代品它不是，也做不到 Hello 的设备绑定强度）。
- 手动 `Win+L` 锁屏不会被自动解开（M5）；连续解锁失败会熔断暂停（M6.6），重录密码恢复。
- 公开分发前必须完成：代码签名、把仓库内 keystore/明文密码配置移出仓库、本模型复核。
